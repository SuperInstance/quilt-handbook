The concept

The Quilt is a git substrate where the task is the atom, state is derived from the record, and provenance is the arbiter.

You push a record to a git repo. The record is an event: "I claim X is true because of parent P with reason R". Records compose into a set. From the set, a pure function called the fold derives the state. State is never stored; it's computed every time you need it, deterministically, from the records.

The fold is a pure function of the record set. Given the same records, every port returns the same state. Given a different set, a different state. State is the result of the fold, not the input.

This sounds like a database. It isn't. It's more like git log + make: every "query" is a rebuild from the source. The source is records in git. The build is the fold. The output is state.

What this buys you:

  • Append-only history. Records are immutable. You can never corrupt the past by writing the future.
  • Offline-first. All you need to compute state is the record set. No central service required.
  • Multi-writer. Anyone can push a record. The fold resolves conflicts deterministically.
  • Provenance is first-class. Every key in state has a "setter" (the record that wrote it) and "losers" (records that tried but were overridden). You can ask "why is X = 5?" and get the answer.
  • Byte-identical across languages. The fold is implemented in 7 languages (TS, Python, Elixir, JS, C#, Perl, C). They all produce the same state for the same input. (Proven: 1000/1000 cross-port fuzz.)

A worked example: one record, one leaf, one root, one fold

Let's trace a single record through the entire pipeline. We'll use the most basic record possible.

{
  "id": "a",
  "kind": "task",
  "parents": [],
  "effects": {},
  "reason": null
}

Five fields. id names the record. kind is its class. parents are the records it derives from (none for the root). effects is what it claims to be true (empty here). reason is a human-readable note.

The leaf: SHA-256 of the canonical JSON

The leaf is the SHA-256 of the canonical form. Canonical form is: keys sorted by Unicode code point, separators are , and : , the literal Unicode is preserved (no \uXXXX escapes), numbers in float64 domain.

canonical = '{"effects": {}, "id": "a", "kind": "task", "parents": [], "reason": null}'
leaf      = sha256(canonical)
         = "229f56e059c1e8209d9e9c0a767ac70f02601f7abe53875069c7d55827533124"

This leaf is the same in Python, JS, C, C#, and Perl. If you change any byte of the input, the leaf changes. If you keep the input identical, the leaf is identical. This is the test of equivalence: 5 ports, 1000 random inputs, 1000 matches.

The closure root: SHA-256 of the ancestor chain

The closure root at a record at is the SHA-256 of the byte string "\n".join("id:hex" for id in sorted(closure_ids(at), by Unicode code point)). For a root record, the closure is just itself.

closure_root("a", records=[a]) = sha256("a:229f56e059c1e8209d9e9c0a767ac70f02601f7abe53875069c7d55827533124")
                            = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"

For a record with parents, the closure includes the parents and their closure roots recursively. If any ancestor is missing, the root is null (incomplete closure).

The fold: state from the set

The fold processes records in topological order (smallest-id-first within a Kahn tier). For each candidate record, for each key in its effects:

  1. If the key is unset in state, the record becomes the setter. State[key] = record's value.
  2. If the key is set, the fold compares classes: override > task > witness. Higher class wins. Losers are tracked in the conflict ledger.
  3. If classes are equal, the descendant wins (deeper record overrides shallower).

For our single record a with empty effects, the fold returns {state: {}, order: ["a"], conflicts: [], orphans: []}. Trivial, but the structure is what scales.

Anatomy of a record

FieldTypeRequiredNotes
idstringyesUnique within the set. The fold sorts by Unicode code point.
kindenumyestask, witness, or override. Class precedence is absolute.
parentsstring[]yesIDs of parent records. Empty array for roots. Missing parent ⇒ orphan.
effectsobjectyesThe claim. Keys are state keys; values are what the record claims they are.
reasonstring | nullyesHuman note. Always present, can be null.

Optional dialect field: digest — a record's own claim of its leaf. The fold never reads this; the runner writes it; the worker verifies it. Format v1 first-class forever; v2 migration is writers-first.

Reserved for v2: signatures (Ed25519 over the leaf), meta (timestamp, author). v1 records will still work; v2 adds provenance crypto.

Write your first record (5 minutes)

You'll create a single record, compute its leaf, derive state from a small set, and verify a checkpoint.

1. Create a record

cat > my-first-record.json <<'EOF'
{
  "id": "task-1",
  "kind": "task",
  "parents": [],
  "effects": { "greeting": "hello, world" },
  "reason": "First record — a task that sets the greeting key"
}
EOF

2. Compute its leaf (Node 18+)

node -e '
import("gitpp-js").then(async (m) => {
  const r = JSON.parse(require("fs").readFileSync("my-first-record.json"));
  console.log("leaf:", await m.recordLeaf(r));
});
' --input-type=module

Output: leaf: 4c1af5c11c4f5ed8d6f1b8b7d0a8e7c6b5a4938271625... (64 hex chars, SHA-256 of canonical form).

3. Fold a small set

cat > set.json <<'EOF'
{
  "records": [
    { "id": "task-1", "kind": "task",    "parents": [], "effects": { "greeting": "hello" },      "reason": null },
    { "id": "task-2", "kind": "task",    "parents": ["task-1"], "effects": { "count": 1 },         "reason": null },
    { "id": "wit-1",  "kind": "witness", "parents": ["task-1"], "effects": { "greeting": "hi" }, "reason": "I saw it differently" }
  ]
}
EOF

curl -X POST http://localhost:8787/fold -H "content-type: application/json" -d @set.json

The fold returns: { state: { greeting: "hello", count: 1 }, order: ["task-1", "task-2", "wit-1"], conflicts: [], orphans: [] }. The witness tried to set greeting but the task outranks it, so hello wins.

Read the spec if you want to understand the fold's rules. §5 is the contract. But for everyday use, "higher class wins, descendant wins, loser's tracked" is enough.

Verify a checkpoint

A checkpoint is a triple {at, state, closureRoot}. Verification answers: "is this state consistent with these records, and is the closure root what we expect?"

curl -X POST http://localhost:8787/verify \
  -H "content-type: application/json" \
  -d '{
    "records": [...],
    "checkpoint": {
      "at": "task-1",
      "state": { "greeting": "hello" },
      "closureRoot": "..."
    }
  }'

Returns one of three verdicts:

  • VERIFIED — state matches, closure root matches, structure is complete
  • STATE-ONLY — state matches but closure root differs (e.g., a later-arriving ancestor or a re-versioned record)
  • MISMATCH — state doesn't match what the records say

Deploy the hub

The hub is the patchwork-quilt/git.pp-ng repo. It includes:

  • The fold (TypeScript port)
  • The runner (writes digests)
  • The worker (verifies digests, runs the fold)
  • The HTTP API (Express + TypeScript)

Public deployment: gitpp.superinstance.dev

Self-host

git clone https://github.com/patchwork-quilt/git.pp-ng
cd git.pp-ng
npm install
npm run build
PORT=8080 npm start

For production, run behind a reverse proxy (nginx, Caddy) with TLS. The hub has no state of its own; it's a stateless function of the records it reads from a git repo.

Write a new fold port (the contract)

To port the fold to a new language, you must implement four functions:

  1. recordLeaf(record) → hex string — SHA-256 of the canonical JSON
  2. closureRoot(records, at) → hex string — SHA-256 of "\n".join("id:hex" for id in sorted closure)
  3. derive(records) → {state, order, conflicts, orphans} — the fold
  4. verifyCheckpoint(records, checkpoint) → {verdict, state, root} — the verifier

The contract is the spec: git.pp-spec. Read §2, §3, §4, §5. The 4 pinned cases in §3.5 are the conformance test — your port must produce the exact same leaves.

Then run the cross-port fuzz: 1000 random float64 records, your port must produce the same SHA-256 leaves as Python, JS, C, C#, Perl.

The hardest part is the number encoding. §3 is the section that catches most new ports. Read it twice, look at the worked example in §2.5, and check the 4 pinned cases.

Troubleshooting

My leaves don't match other ports

99% of the time, it's the number encoding. Check:

  • Integer form requires |v| < 1e16. Values 1e16 to 1e21 use scientific.
  • Use 15/16/17 sig-digit fallback with round-trip check. Skip the integer form when |v| >= 1e16.
  • Use e+02 format (zero-padded 2-digit exponent), not e+2.
  • Trailing zeros stripped: 2.50000e+10 becomes 2.5e+10.

Look at gitpp-cross-port/CLleaf.c for the C99 implementation; the algorithm is language-agnostic.

JSON parse loses precision for large floats

JSON.parse in JS converts -6.196169307310858e+20 to -619616930731085800000 (loses the last 4 digits). Same for any value with 16+ significant digits. Workarounds:

  • Pass the record as a raw JSON string and parse with a custom JSON parser that handles arbitrary-precision numbers.
  • Use a JSON library that supports BigDecimal/BigInt (e.g., json-bigint for Node).
  • For the cross-port fuzz specifically, the runner at gitpp-cross-port/fuzz.mjs writes each record's raw JSON text to disk and pipes it to each port, avoiding the JS precision loss.

My closure root doesn't match

Check:

  • Parents are sorted by Unicode code point, not alphabetical.
  • The join string is \n (LF), not \r\n.
  • Each line is id:hex with NO space after the colon.
  • The SHA-256 is over the joined bytes, not the joined string with extra whitespace.

My fold produces different state

Read §5 carefully. The class precedence is absolute (override > task > witness). Within a class, the most-derived record wins (deeper in the parent chain). When equal, ancestor depth breaks ties. The conflict ledger tracks every loser for every key.

If you're still stuck, file an issue with a minimal repro and post the cross-port diff.
